Crea el schema GraphQL con tipos realesCódigo

Guarda esto como schema.graphql. Incluye tipos para probar todos los resolvers.

type User {
  id: ID!
  name: String!
  email: String!
  status: String
  role: String
  createdAt: String
}

type Order {
  id: ID!
  userId: ID!
  total: Float!
  status: String!
  createdAt: String
}

type UserConnection { items: [User], nextToken: String, scannedCount: Int }
type OrderConnection { items: [Order], nextToken: String, scannedCount: Int }

type Query {
  getUser(id: ID!): User
  listUsers(limit: Int, nextToken: String): UserConnection
  getUsersByStatus(status: String!): UserConnection
  listOrders(userId: ID!): OrderConnection
}

type Mutation {
  createUser(name: String!, email: String!, role: String): User
  updateUserStatus(id: ID!, status: String!): User
  deleteUser(id: ID!): User
}

schema { query: Query; mutation: Mutation }

Resolver Runner & FilterExpression

Probar el Resolver Runner directo y los filtros DynamoDB
Crear resolver con FilterExpressionCódigo

Crea Query.getUsersByStatus.request.js:

export function request(ctx) {
  return {
    operation: 'Scan',
    filter: {
      expression: '#s = :status',
      expressionNames: { '#s': 'status' },
      expressionValues: { ':status': { S: ctx.arguments.status } },
    },
  };
}

export function response(ctx) {
  return ctx.result;
}
ℹ Nota

Puedes poner request y response en el mismo archivo o en archivos separados. Ambos formatos funcionan.

Ejecutar desde Resolver RunnerAcción

Ve a la pestaña Resolver Runner en el panel y completa:

  • Type.Field: Query.getUsersByStatus
  • Identity: cognitoUser
  • Arguments:
{ "status": "active" }

Haz clic en ▶ Run Resolver.

✓ Qué esperar en el trace

El trace muestra:
• [REQUEST] — operación Scan con FilterExpression
• [RESPONSE] — items filtrados: solo usr-001 y usr-002 (status = active)
• El resultado NO incluye usr-003 (status = inactive)

Verificar historial de runsAcción

Haz clic en Recent Runs (abajo del trace) para expandir.

✓ Qué esperar

Aparece la ejecución anterior con ✓ verde, badge de identidad cognitoUser y timestamp. Al hacer clic sobre ella, los campos Type.Field, Identity y Arguments se restauran automáticamente.

Resolvers VTL

Verificar evaluación local de templates Velocity
Crear un resolver VTLCódigo

Crea Query.listOrders.request.vtl:

{
  "operation": "Query",
  "query": {
    "expression": "userId = :uid",
    "expressionValues": {
      ":uid": $util.dynamodb.toDynamoDBJson($ctx.args.userId)
    }
  }
}

Crea Query.listOrders.response.vtl:

$util.toJson($ctx.result)
Probar el resolver VTLAcción

En Resolver Runner:

  • Type.Field: Query.listOrders
  • Arguments: { "userId": "usr-001" }
✓ Qué esperar

El trace muestra la operación Query con la expresión VTL ya evaluada. Resultado: items con ord-001 y ord-002 (userId = usr-001), NO ord-003.

ℹ GSI Simulation

Aunque userId no es la PK de la tabla Order, la extensión simula el GSI filtrando todos los items por ese atributo. No necesitas definir el índice explícitamente en mock-data.json.

Agrega la mutación al schema. Luego crea estos archivos:

Mutation.createUser.pipeline.json

{
  "functions": [
    { "name": "ValidateEmail", "dataSource": "NONE" },
    { "name": "SaveUser", "dataSource": "User" }
  ]
}

functions/ValidateEmail.request.js

export function request(ctx) {
  // Guardar en stash para las funciones siguientes
  ctx.stash.email = ctx.arguments.email;
  ctx.stash.validatedAt = '2024-01-01T00:00:00Z';
  if (!ctx.arguments.email.includes('@')) {
    $util.error('Invalid email format', 'ValidationError');
  }
  return {};
}

export function response(ctx) {
  return { validated: true };
}

functions/SaveUser.request.js

export function request(ctx) {
  // ctx.prev.result = resultado de ValidateEmail
  return {
    operation: 'PutItem',
    key: { id: { S: $util.autoId() } },
    attributeValues: {
      name: { S: ctx.arguments.name },
      email: { S: ctx.stash.email },
      role: { S: ctx.arguments.role || 'user' },
      status: { S: 'active' },
    },
  };
}

export function response(ctx) {
  return ctx.result;
}

Operaciones DynamoDB completas

UpdateExpression, paginación, composite keys
UpdateItem con UpdateExpressionCódigo

Crea Mutation.updateUserStatus.request.js:

export function request(ctx) {
  return {
    operation: 'UpdateItem',
    key: { id: { S: ctx.arguments.id } },
    update: {
      expression: 'SET #st = :status',
      expressionNames: { '#st': 'status' },
      expressionValues: { ':status': { S: ctx.arguments.status } },
    },
  };
}

export function response(ctx) {
  return ctx.result;
}

En Resolver Runner con:

{ "id": "usr-003", "status": "active" }
✓ Qué esperar

El usuario usr-003 (Laura) ahora tiene status: "active". Corre Query.getUsersByStatus de nuevo con "status": "active" — ahora debe devolver los 3 usuarios.

Paginación con limit + nextTokenAcción

Crea Query.listUsers.request.js con soporte de paginación:

export function request(ctx) {
  return {
    operation: 'Scan',
    limit: ctx.arguments.limit || 2,
    nextToken: ctx.arguments.nextToken || null,
  };
}

En el Resolver Runner usa { "limit": 2 }. El resultado devuelve 2 usuarios y un nextToken. Pega ese token como argumento para obtener la siguiente página.

✓ Qué esperar

Página 1: 2 items + nextToken: "MQ==" (o similar en base64).
Página 2 con ese nextToken: 1 item + nextToken: null (fin de datos).

Validate Stack IntentAcción

Después de un cdk synth, ejecuta:

AWS: Validate Stack Intent (cdk.out)
✓ Qué esperar

Abre un panel con findings agrupados por severidad (Critical → Low) y un Confidence Score 0–100 con label: Ready to Deploy / Review Needed / etc. Cero findings críticos en un proyecto limpio.

Validate Environment VariablesAcción
AWS: Validate Environment Variables
✓ Qué esperar

Lista cada Lambda con sus env vars clasificadas: static (resuelta), ssm (necesita cloud), secret, token (CDK intrínseco). Si hay SSM refs no resueltas, sugiere el snippet para .env.local.

CDK Diff ExplainerAcción

AWS: Run CDK Diff Explainer
✓ Qué esperar

Cada cambio tiene: tipo de recurso, nivel de riesgo (🔴 Critical / 🟠 High / 🟡 Medium / 🟢 Low), explicación en lenguaje natural, y recomendación. El botón "Export Markdown" genera el reporte para PR review.

Lambda Debugging (si tienes Lambda data sources)

Adjuntar VS Code debugger a un handler local
Configurar un Lambda handlerConfig

En .vscode/settings.json:

{
  "awsToolkit.appsync.lambdaHandlers": {
    "UserLambdaDS": "src/handlers/users.ts#handler"
  },
  "awsToolkit.appsync.lambdaDebugPort": 9229
}

Crea el handler en src/handlers/users.ts:

export async function handler(event: any) {
  // Pon un breakpoint aquí ↓
  const { arguments: args, identity } = event;
  return { id: args.id, name: 'From Lambda', identity };
}
ℹ Flujo de debug

1. Pon un breakpoint en el handler.
2. En Resolver Runner selecciona el resolver que usa UserLambdaDS.
3. Haz clic en 🐛 Debug Lambda.
4. VS Code adjunta automáticamente el debugger — la ejecución pausa en el breakpoint.
5. Cuando continues (F5), el resultado aparece en el trace del panel.

AWS Service Map

Mapa visual interactivo de servicios generado desde cdk.out — React Flow
Generar el mapa de serviciosAcción

Requiere que cdk.out/ exista. Si no lo tienes, corre primero:

cdk synth

Luego ejecuta desde el Command Palette (Cmd+Shift+P):

AWS: Generate Service Map
✓ Qué esperar

Se abre el panel AWS Service Map con un diagrama React Flow interactivo:
• Un tab por stack CDK (uno por cada *.template.json en cdk.out/).
• Nodos auto-posicionados de izquierda a derecha por tipo de servicio.
• Conexiones con etiquetas que indican el tipo de relación.
• Leyenda dinámica en la barra superior con solo los servicios presentes en el stack.

⚠ Si no aparecen nodos

La extensión lee cdk.out/*.template.json — no el código CDK fuente. Verifica que cdk synth haya completado sin errores y que el directorio no esté vacío.

Verificar conexiones y explorar el mapaVerificar

Para el stack de este proyecto (AppSync + Lambda + DynamoDB + Cognito), el mapa debería mostrar este flujo:

Cognito ──auth──▶ AppSync ──datasource──▶ DataSource ──invokes──▶ Lambda ──env ref──▶ DynamoDB
ℹ Conexiones que detecta automáticamente

datasource — AppSync DataSource con ApiId: {Ref: ...}
invokes — DataSource tipo AWS_LAMBDA con LambdaFunctionArn
reads/writes — DataSource tipo AMAZON_DYNAMODB con TableName
auth — AppSync con UserPoolConfig.UserPoolId
triggers — AWS::Lambda::EventSourceMapping (SQS/SNS → Lambda)
env ref — Lambda con referencias a tablas/colas en Environment.Variables

Prueba la interactividad del panel:

  • Arrastrar nodos — reorganiza el layout a tu gusto
  • Scroll / pinch — zoom in/out
  • MiniMap (esquina inf. derecha) — navegación rápida en stacks grandes
  • Controls (esquina inf. izquierda) — fit view, zoom buttons
  • Tabs — cambia entre stacks CDK si tienes más de uno
✓ Edges animados

Las relaciones triggers e invokes muestran un edge animado (línea de puntos en movimiento) para distinguir flujos de datos activos de referencias de configuración.
